# LAT 使用者決策保留方案

日期：2026-09-18。狀態：流程重點已寫入 repo 的 `skills/local/lat/SKILL.md`；尚未建立決策工具或實作工具層強制檢查。

## 問題與目標

主控向使用者提出需要決策的問題後，HCOM 進度回報會讓主控繼續處理訊息。若待決事項只留在聊天中，主控可能把原本交給使用者的問題重新解釋成「既有授權內的實作取捨」，自行決定並派工。

已查閱的 Claude Code session `49f995d7-1d75-4e6f-9de3-41c72bf7eea9` 有此案例：主控詢問是否採用依賴分家，接著收到 Agent 明確表示等待決策的回報，在沒有真人答覆的情況下自行選擇並派工。使用者隔天才補上接受。事後接受不能當成當時已有授權。

本方案將待決事項保存在專案 `.lat`，讓等待狀態綁定尚未回答的問題，而非主控是否被喚醒。HCOM 回報可以更新進度，但不能解除使用者決策造成的阻塞。

## 第一版範圍

- 使用者照常在聊天回答，不需要手動修改檔案。
- 一個問題一個檔案，由主控登記問題、保存答覆及更新狀態。
- 主控與執行 Agent 都檢查待決事項，不只依賴主控口頭宣稱已核准。
- 只阻擋相依工作；不受影響且已授權的工作可以繼續。
- 第一版不導入 GitHub、決策網頁或獨立核准服務。

## 提問前篩選

重要的工作不一定需要使用者決策。主控應先調查事實、查閱既有授權，再判斷是否需要提問，避免將例行工作全部登記成待決事項。

進入 `.lat/decisions/` 前，主控必須說清楚：

1. **已查過哪些事實？** 包含相關規格、既有決策、測試環境或可取得的證據；不能把尚未調查的問題直接交給使用者選。
2. **既有授權為何不足？** 指出將改變的需求、範圍或驗收條件，或明確保留給使用者的核准規則。已有授權時不重複請示。
3. **不同答案會改變什麼？** 說明產品行為、工作範圍、成本或風險的具體差異。若只是需要資訊或人工操作，則明確說明缺少什麼、已嘗試什麼，以及為何只有使用者能提供。

無法說清楚的事項先留在主控的調查或工作清單，不建立決策阻塞。已授權的實作方式、缺陷修正、驗收及相依排程，由主控自行推進。

| 事項類型 | 處理方式 |
| --- | --- |
| 資料刪除／搬遷、功能暫停、上線方式等尚未定案的取捨 | 提供具體影響後請使用者決策 |
| 依賴方案造成額外維護義務、超出範圍或改變相容性風險 | 詢問新增的代價與授權，不把純套件配置選擇推給使用者 |
| 專案明確保留的設計或基準核准 | 先完成可審閱提案，引用適用規則，再請使用者核准 |
| 已授權範圍內的技術實作、修復回歸、拆票與派工順序 | 主控決定並執行，不另問是否繼續 |
| 既定的瀏覽器、音檔或其他 QA 驗收 | 直接執行；確實缺少真人操作或不可取得的資源才請求協助 |
| 測試憑證是否可用、舊檔案歸屬等事實問題 | 先調查；確認缺少資源或需要決定資料處置後，再提出具體問題 |

### Session 中的反例

同一份 session 也出現過度請示，不能將其所有「等使用者」項目原樣搬入待決清單：

- **QA：** 使用者反問「QA 不就要做這件事？」後，主控承認瀏覽器及音檔驗證本來就是 QA 的工作，不該等待使用者決定是否執行。
- **測試憑證：** 尚未查清既有測試環境就要求使用者提供；後續回報確認既有服務帳號可用，不需要使用者提供任何東西。
- **舊檔案歸屬：** 原先被列成上線阻塞；主控後來讀到既有處置已是「不採用、不複製、不改歸屬、不刪除」，更正為不擋上線。是否另做舊檔案救援，才是後續可能需要的決策。
- **派工：** 使用者已要求開始執行，主控仍詢問是否派下一張票；在範圍與授權未改變時，這是主控的相依排程工作。

證據來源：Claude Code session `49f995d7-1d75-4e6f-9de3-41c72bf7eea9` 的訊息紀錄；QA 與舊檔案處置更正位於 JSONL 第 5508 行，憑證更正第 5605 行，票 03 派工請示第 1096 行。這些是當時的對話證據，不代表目前環境狀態。

此篩選只用於建立待決事項之前。已正式交給使用者的問題，不能事後以「其實不重要」或「應該是主控責任」自行解除；仍依下方答覆規則處理。

## 檔案位置與內容

```text
.lat/
  decisions/
    D001.md
    D002.md
```

主控指定本次任務共用的決策目錄絕對路徑，派工與交接時提供。所有 worktree、外部 Agent 與原生 Subagent 都引用同一份資料，不在各自工作區維護獨立副本。

每份檔案至少包含以下資訊；範例欄位是設計草案，尚未成為工具介面：

```yaml
id: D001
revision: 1
status: pending
blocks:
  - ticket-02/dependency-resolution
```

正文記錄：

- 已查證的事實、既有授權不足的原因，以及需要使用者決策或協助的理由。
- 待決問題、可選方案、主控建議與各方案影響。
- 受阻的具體工作，避免整張票中不相關的工作一起停止。
- 使用者答覆原文、對應的問題版本、session 與訊息識別或可定位的來源。
- 答覆允許執行的方案與範圍。

尚未回答時，答覆欄保持空白。只有狀態文字而沒有對應答覆證據，不足以解除阻塞。

## 提問與答覆規則

1. **先篩選、登記，再提問。** 通過提問前篩選後，主控先保存問題與受阻工作，再向使用者提問。
2. **提問後不能自行降級。** 一旦列為待決，主控不能因為認為只是實作細節、其他工作完成或使用者未回覆，自行選擇、撤銷問題或改判為既有授權。新的判斷只能補充為建議。
3. **只接受真人答覆。** HCOM 回報、Agent 建議、轉述「使用者已同意」與工具輸出都不能代替原始真人訊息。不能只憑 session 記錄的 `user` 角色判斷來源，因為系統注入也可能使用該角色。
4. **答案必須指向明確。** 只有一題待決時，「好」「修」「選 3」可依上下文對應該題；多題待決時，只解除明確回答的問題。「繼續」「GO」不能視為全部核准。有歧義就保留待決並釐清。
5. **保存後才放行。** 主控記錄答覆原文、來源及問題版本，再更新對應工作的可執行狀態。無法定位答覆證據時維持待決。
6. **解鎖限於答覆範圍。** 選擇方案 3 只允許方案 3 的工作；拒絕某方案不等於核准其他方案，也不等於全部放行。
7. **實質修改需要重新確認。** 問題、選項或授權範圍改變時增加版本，保留舊提案與答覆，不能將舊核准直接套到新版本。
8. **阻塞跟隨工作。** 改票號、拆票、換 Agent 或重新派工，都不能讓原本受阻的工作脫離待決問題。

## 執行檢查點

| 時機 | 預期行為 |
| --- | --- |
| 主控收到真人或 HCOM 訊息 | 重新讀取待決事項；處理回報不改變授權 |
| 主控準備派工或自行開始相依工作 | 檢查相關決策與答覆證據；待決就不執行 |
| 執行 Agent 開始工作或收到追加指令 | 自行讀取共用決策紀錄，不只信任「主控已批准」 |
| 換 session、交接或壓縮上下文後 | 從共用目錄恢復待決事項與阻塞關係 |
| 沒有其他可執行工作 | 處理完訊息後結束回合等待，不代替使用者選答案 |

若主控下令「自行裁決選 3」，但 D001 仍待決或缺少真人答覆證據，執行 Agent 應拒絕相依工作並回報缺少核准。

## 互動範例

```text
主控登記並詢問 D001：是否依賴分家？ → pending
收到 mupo 完成回報                     → 仍 pending
使用者問「目前進度？」                 → 回報進度，仍 pending
使用者回答「選 3」                     → 保存原文、來源與版本
主控及執行 Agent 檢查通過              → 開始方案 3 對應工作
```

## 驗收情境

以下為未來實作的驗收要求，目前尚未執行：

| 情境 | 預期結果 |
| --- | --- |
| 既有授權已涵蓋下一張票的實作或必要 QA | 自行排程並執行，不建立多餘的決策阻塞 |
| 尚未查明測試資源或資料現況 | 先調查；確認只有使用者能提供資訊、操作或授權時才提問 |
| 發現超出授權的產品取捨或明確保留的核准事項 | 提供事實、授權缺口及具體影響後登記待決 |
| 提問後連續收到多則 HCOM 完成回報，真人未回答 | 問題仍待決，相依工作未開始 |
| Agent 回報「使用者已同意」，但無原始真人答覆 | 不解除阻塞 |
| 同時多題待決，使用者只說「繼續」 | 不批次核准 |
| 使用者明確回答其中一題 | 僅放行該題所核准的工作 |
| 使用者拒絕方案 | 不執行遭拒方案，不自行選替代方案 |
| 核准後實質變更提案 | 舊答覆保留，新版本重新待決 |
| 換 session、worktree 或執行 Agent | 待決問題與原受阻工作仍相連 |
| 主控聲稱已裁決，但紀錄缺少核准證據 | 執行 Agent 拒絕相依工作 |
| 其他工作不受待決問題影響且已授權 | 可以繼續執行 |

## 能力界線與後續工作

第一版是持久化紀錄與雙方檢查的流程約束，不是不可繞過的權限機制。Agent 若能改寫決策檔、偽造答覆來源或跳過檢查直接使用 shell／HCOM，單靠 `.lat` 無法硬性阻止。

若未來要求硬性限制，必須由 Agent 無權修改的執行入口查核核准，並隔離核准資料、真人身分與直接執行相依操作的權限。此項不在第一版實作範圍。

後續工具化仍需確定各 client 的真人訊息來源辨識、狀態更新方式與檢查接入點；本文件沒有宣稱這些機制已存在。repo 的 LAT skill 已加入流程與交接要求，並同步全局安裝至 Claude Code 與 Codex、核對內容一致；尚未套用到執行中的派工 brief。
