# 每張票只跑受影響測試，整套只在整批合併後與發布前執行

ADR 0005 的閘門只擋得下「程式內容完全相同」的重跑；每張票仍各跑一次整套，26 小時內主機跑了 106 次整套（spotify-controller 每次約 24 分鐘）。需求見 ouob-tw/LoopAgentTeams-work#226（使用者決定 RAPO-TEST-1 至 RAPO-TEST-11）。

## 決定

1. **每張票只跑受影響的測試；整套只在整批合併後跑一次，推送到 main 或推送版本標籤前再確認一次。**
   - 為什麼：每票整套是最大的時間花費；合併後那次整套仍在交付前把關。
   - 代價：跨票互相影響的問題延到整批合併後才發現，要回頭找是哪張票造成的。

2. **受影響測試由各專案進版控的對照表（程式路徑 → 測試）決定，由閘門依改動檔案算出；改到未列入的檔案或共用路徑時自動改跑整套。**
   - 為什麼：結果固定、可核對，hook 能據此擋下票內整套；不採用測試工具內建的變更偵測（各語言支援不一）或呼叫關係推算（成本高、難核對）。
   - 代價：對照表漏列關聯時會漏跑受影響測試，只能靠合併後的整套攔下；新增檔案時由實作者補表、審查者核對。
   - 退回的範圍（ouob-tw/LoopAgentTeams-work#311）：觸發的檔案都落在某幾套整套的執行目錄內時只跑那幾套，其餘選出的測試照常跑；有觸發檔不在任何套件目錄內才跑全部整套。登記檔 `.suite-gate.json` 只新增或修改對照規則時只跑那些規則對到的測試，刪除規則或改到其他欄位仍跑全部整套。代價是共用檔影響到別套時要等合併後的整套才攔下。

3. **已有對照表的專案，整套執行須標明用途；用途寫進紀錄但不進指紋。**
   - 為什麼：不必分辨「票的工作區」與「整合工作區」也能擋下票內整套；用途不進指紋，整批合併後的通過紀錄可被發布前檢查直接沿用，不改變 ADR 0005 的沿用規則。
   - 代價：合併後與發布前的執行者要記得帶用途；漏帶會被擋下並收到提示。

4. **發布前把關用 Git pre-push hook 查閘門紀錄，只查不跑。**
   - 為什麼：發布是 Git 動作，在推送前攔截最可靠；內容相同時不花任何測試時間。
   - 代價：pre-push 是每個 repo 各自安裝的本機設定；`--no-verify` 可略過。

5. **定期整理由閘門在整套執行後觸發（超過 30 天，或整套時間比整理後基準多 30% 以上），在 tracker 開整理票，同一專案同時只有一張。**
   - 為什麼：跟著實際使用觸發，不活躍的專案不會被打擾，也能在未滿一個月但已明顯變慢時處理；Claude 雲端排程看不到本機專案。
   - 代價：完全不跑整套的專案不會被提醒；整理票的刪除與合併直接由 Agent 執行，保護範圍只由審查把關。
