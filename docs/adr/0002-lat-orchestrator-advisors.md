# LAT 主控參謀：兩家模型各一位，先過參謀才問使用者，參謀不能放寬授權

主控有了問題面板後，常把已授權範圍內的事也丟給使用者決定（需求見 ouob-tw/LoopAgentTeams-work#67）。我們因此決定：每個主控配兩位參謀，主控要發 DECIDE 或 HELP 前先交給參謀判斷，參謀認定需要真人才問使用者。細節做法見 `skills/local/lat/references/advisors.md`，本文只記錄不看脈絡會覺得奇怪的取捨。

## 決定

1. **參謀只能在既有真人授權內定案，而且必須引用授權來源。**
   引用的必須是已確認 Spec 的段落，或有真人答覆證據的待決紀錄；引用不到就只能判「需要真人」。已經問過使用者的題目，只有真人能解除。
   - 為什麼：目標是減少主控「不必要的提問」，不是讓 AI 替使用者放寬授權。要求引用來源，讓執行 Agent 能核對參謀定案，不必把參謀意見當成真人核准。
   - 代價：授權寫得含糊時，參謀只能判需要真人，提問不會減少。

2. **一位 Claude、一位 Codex，各自獨立判斷；不一致時先互看理由再議一輪。**
   - 為什麼：同家模型容易一起犯同一種錯。多議一輪的成本比打擾使用者低；仍不一致才交給使用者，並附雙方說法。
   - 代價：每次諮詢兩份額度。某一家不可用時改用兩位同家參謀並註明降級，不退回直接問使用者。

3. **參謀常駐，在階段交界（Spec 確認後、每批票整合完）關閉，下次需要時才開全新參謀；不寫交接摘要。**
   - 為什麼不每次都開新的：使用者偏好讓參謀保留同一階段內的脈絡。
   - 為什麼不一直常駐：長上下文會腐化，階段交界是自然的清空點。
   - 為什麼不寫交接摘要：Spec 與待決紀錄已保存每次判斷與理由，就是現成的交接資料，不另外維護摘要（使用者選擇時，選項也提到摘要可能帶入舊上下文的偏差）。

4. **用工具強制：結束回合的 DECIDE 檢查要求每題都有參謀行。**
   參謀行為 `needs-human`、`exempt <類別>` 或 `late <結論>`。例外類別固定為 Spec 確認、需求討論、帳號額度三種。
   - 為什麼：先前經驗是只寫規則擋不住（見 ouob-tw/LoopAgentTeams-work#57）。工具只能核對紀錄格式，無法證明真的諮詢過，這是可接受的界線。

5. **參謀照常建任務卡、受停住監控看管，回覆後以完整 HCOM 名稱登記待命，回覆主控用 `--intent inform`。**
   - 為什麼：參謀停住或消失時，主控必須被叫醒，不能永遠等。實測發現短名登記不生效、以 request 回覆會被 HCOM 的「未回應」通知解除待命，所以這兩點寫進做法（ouob-tw/LoopAgentTeams-work#73、#75）。

## 刻意不寫進決定的事

- 參謀與 Codex 模型、effort 是設定值，依 hcom-spawn 與 `references/agents.md` 調整。
- 等待登記被系統通知解除、互相等待、等待對象消失等監控面的缺口另案處理（ouob-tw/LoopAgentTeams-work#76、#77）。
