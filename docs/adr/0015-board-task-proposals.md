# 任務提案：經本機連線送出並查證提案者，一律 passkey 核准

使用者在對話中想新增自動化任務，但讓 Agent 直接寫看板資料，等於讓 Agent 自己決定主機上定時跑什麼（Spec ouob-tw/LoopAgentTeams-work#699，共識 v4）。

## 決定

1. **送出與撤回走本機連線，查詢走共用資料夾。** 看板在使用者層級的狀態資料夾開只有本人可用的 Unix socket；提案與結果由看板寫成檔案，查詢與等待只讀結果檔，不需要看板在執行。結果檔先寫暫存檔再 hard link 到位，核准、拒絕、過期、撤回只有先寫成功的算數；核准的內容保存在結果檔，任務只照它建立。
   - 為什麼：與看板提問（[ADR 0009](0009-board-asks-shared-folder.md)）不同，提案要知道是誰送的，只靠檔案查不出送出的程序。
   - 代價：看板沒在執行時送不出提案。

2. **提案者比照 pd 查證。** 看板看管的一支 Python 接收程式對每條連線用 SO_PEERCRED 取得程序，沿父程序找到 `claude` 或 `codex`，以 hcom 目前的紀錄對到 HCOM 名稱；查不到就拒收，不接受自稱。是不是 LAT 主控依 LAT session 紀錄另外標示。
   - 為什麼：Node 取不到 socket 對端憑證；卡片上的名稱要是看板查到的。
   - 代價：看板多一支要看管的子程序，只有接 HCOM 的 Agent 能提案。

3. **一律用看板的 passkey 核准，核准綁定卡片顯示的內容。** 不接受口頭同意或 Agent 轉述；pd 的 passkey 與測試用登入不能核准。使用者自己在看板新增任務不需要 passkey。
   - 為什麼：程式無法證明轉述的「使用者同意了」。

4. **結果通知只盡力送一次。** 看板依提案者的 HCOM session ID 找目前名稱傳訊，找不到或不只一個就不傳；結果檔是唯一依據。

## 安全邊界

Agent 與看板用同一個系統帳號執行，Agent 技術上仍能直接改看板的狀態資料夾。passkey 核准擋的是「Agent 未經同意自行建任務」的正常流程，不是防竄改，和 pd 的「程序樹查證，非防竄改」同一級別。
