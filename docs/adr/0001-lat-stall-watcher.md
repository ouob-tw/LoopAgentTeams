# LAT 停住監控：每個主控一支背景監控，用視窗輸入喚醒

LAT 的 Agent 會在還有工作時停住（需求與案例見 ouob-tw/LoopAgentTeams-work#36、#12）。#12 查到的 5 個真實案例，停住時 Agent 都已經結束回合、不在工作，所以只靠技能規則叫不醒它。我們因此決定：每個主控 session 帶一支背景監控程式（`lat-watch`），由它判斷停住並採取行動。細節行為見 `skills/local/lat/references/stall-watch.md`，本文只記錄不看脈絡會覺得奇怪的取捨。

## 決定

1. **每個主控一支監控程序，不做全域常駐服務，也不只靠規則。**
   `lat-session activate` 啟動、`deactivate` 停止，compact／resume 的恢復 hook 發現 session 仍在但監控不在時重新啟動。
   - 為什麼不只靠規則：停住發生在 Agent 已結束回合之後，沒有任何規則會再被執行。
   - 為什麼不做全域服務：多個主控各自監控自己派出的 Agent，生命週期跟著 LAT 走，不需要另外安裝、手動開關，也不會監控到不屬於 LAT 的 Agent。
   - 代價：監控掛掉就只有該主控失去保護，要靠下一次恢復才會帶回來。

2. **「有進展」以紀錄檔變動或 HCOM 事件判定，事件以 session ID 歸屬。**
   HCOM 的狀態會卡在 `active`，不能當依據；短名稱會撞名，#50、#51 就是把別的 Agent 的事件或訊息算到對方身上。因此一切歸屬都用 `hcom list --json` 給的確切 session，不用短名稱。

3. **要求 Agent 明確宣告等待，而不是由監控猜哪些等待是正當的。**
   Agent 或主控結束回合前，用 `lat-watch wait` 寫明在等誰（決策或 Agent）。收到新訊息、等待的決策不再 pending、等待的 Agent 送出訊息時失效，之後要再等得重新宣告。
   - 為什麼：猜測會誤報（長時間等待被催）或漏報（真的停住被當成在等）。宣告把判斷責任放在知道內情的一方，失效條件讓下一次真的停住仍會被抓到。
   - 代價：Agent 要遵守規則；沒遵守的結果就是被催一次，成本低。

4. **喚醒用終端機輸入（inject），不用 HCOM 訊息。**
   HCOM 在狀態卡在 `active`、或輸入框有字時會把訊息扣住不送（上游 aannoo/hcom#151），而這正是需要喚醒的情況。所以催促直接輸入到該 Agent 的視窗。每段停住只催一次。

5. **輸入框有殘留文字時，先備份再清；清除一旦沒有變短就停手。**
   殘留文字加上排隊中的訊息，會讓訊息永遠送不進去（#12 的一個字母案例）。監控在文字 5 分鐘沒變、而且確有訊息排隊時，把原文存檔，逐字元刪除，並通知使用者與主控附上原文。
   - 為什麼要檢查有沒有變短：工具介面上的文字（如核准提示）看起來可能像輸入，若刪除後長度不減，代表那不是真的輸入，繼續按退格可能誤觸介面，所以停手並回報。
   - 為什麼先備份：那也可能是使用者打到一半的內容，必須能還原。文字有變動（使用者還在打）或沒有排隊訊息時不動手。

6. **逐層上報：執行 Agent → 主控 → 使用者；使用者只在三種情況被打擾。**
   催過仍沒恢復的執行 Agent 先通知它的主控；主控在時限內沒處理才通知使用者；主控自己催過仍沒恢復也通知使用者；輸入框文字被清除時通知使用者。使用者通知用 Herdr 彈出通知加主控對話裡的一則說明，沒有 Herdr 時只留說明。
   - 為什麼：使用者的注意力是最貴的資源，大部分停住應由主控吸收。
   - 另有兩種「可能掛住的指令」「等核准」只通知上一層，不催，因為那時 Agent 並沒有閒著。

## 刻意不寫進決定的事

- 門檻（閒置 10 分鐘、狀態卡住 20 分鐘、輸入框文字 5 分鐘）是設定值，隨實測調整，不屬於架構。
- 是否把 stale `active` 的問題回報給 HCOM 上游，由使用者另外決定。

## 影響

- 判斷邏輯集中在一個不接觸外部的純函式，觀察與動作可換成假的，所以行為可用時間序列測試。
- 監控動作只靠 HCOM 與終端機現有指令完成，不修改 HCOM、Codex 或 Claude Code。若上游修好 #151，第 4 點的理由就會消失，應重新評估是否仍需終端機輸入。
