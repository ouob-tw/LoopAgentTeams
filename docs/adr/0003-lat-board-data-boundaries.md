# LAT 看板：只透過輔助工具讀寫問題檔、狀態不看 Herdr、傳話走輸入框、回報放共用目錄

使用者要一個網頁看板，在一個畫面看所有專案的 LAT 主控、收回報、回答待決題並傳話（需求見 ouob-tw/LoopAgentTeams-work#105）。以下四個決定劃定看板與既有 LAT 工具之間的界線。

## 決定

1. **看板伺服器端用 TypeScript，讀寫問題檔一律呼叫 Python 面板輔助工具的指令；既有 Python 不改寫。**
   - 為什麼：問題檔的格式、檔案鎖、面板紀錄與來源雜湊只有一份 Python 實作，Herdr 待答面板也在用。看板自己再寫一份，改格式時就要兩邊一起改，改漏會寫壞問題檔。使用者被問過是否要把整個專案改成 TypeScript，選擇維持現狀。
   - 代價：主機要同時有 Bun 或 Node 與 Python；每次讀寫要啟動一次 Python。因此看板以檔案監看觸發重讀，不以固定短間隔反覆呼叫。
   - 2026-10-22 補記（ouob-tw/LoopAgentTeams-work#221）：有兩處是刻意的固定間隔，不違反上面這句。其一是保底重讀（`board.ts` 的 `fallbackGapMs`）：檔案監看會漏掉變動，而且 Herdr 與 hcom 的 Agent 清單變動不會動到任何被監看的檔案，只能靠它補上；間隔由 `LAT_BOARD_FALLBACK_SECONDS` 決定（5 到 60，預設 60），實際間隔再扣掉一次讀取最長的逾時，所以最慢 60 秒。其二是額度輪詢（`quota.ts` 的 `createQuotaPoller`）：額度資料在 claude-swap 與 codex-multi-auth 自己的檔案裡，不在看板監看的範圍，也不是由看板的檔案變動觸發，所以每 `LAT_BOARD_QUOTA_SECONDS` 秒（預設 30）讀一次，所有瀏覽器共用，上一次還沒讀完就不再啟動。這兩處都不是「固定短間隔反覆呼叫輔助工具」：保底重讀是漏掉時的補救，額度輪詢不呼叫 LAT 的 Python 輔助工具：Claude 那半每次啟動一次 claude-swap 的 `list --json --cached-only`（另一個程序，只讀它自己的快取、不連網），Codex 那半直接讀 codex-multi-auth 的檔案；所以間隔不能壓得很短，預設 30 秒。
   - 2026-10-28 補記（pd 待核准，bw-broker ticket 06）：第三處是 pd 輪詢（`pd.ts` 的 `createPdPoller`）：待核准請求在 pd 服務裡，不在任何檔案，只能每 `LAT_BOARD_PD_SECONDS` 秒（預設 5）執行一次 `pd pending --json`（另一個程序，經 Unix socket 問 pd 服務，不呼叫 LAT 的輔助工具），所有瀏覽器共用，上一次還沒讀完就不再啟動。請求預設最多等 2 分鐘，間隔比額度短才看得到；拒絕後另外立刻讀一次。

2. **看板的主控狀態只用 LAT 自己的資料判斷，不讀 Herdr 的 Agent 狀態。**
   狀態來自面板綁定登記（是否啟用）、問題檔（是否有未送出的待答題）與主控回報紀錄（最新一筆的標籤）。
   - 為什麼：被 HCOM 包住的 client，Herdr 回報的狀態會與實際不符（見 `docs/herdr-hcom-status-research.md`）。依賴它，看板的狀態就不可信。
   - 代價：看板分不出「正在執行指令」與「停在等待」這種更細的狀態；停住監控的通知這一版也不顯示。
   - 2026-10-16 補記（ouob-tw/LoopAgentTeams-work#130）：client 是否還在，改看 hcom 的 Agent 清單（`hcom list --json`）。有面板綁定、但 session ID 不在清單上的主控顯示為「已關閉」，處理方式與已結束相同；面板綁定照舊不動。hcom 清單不是 Herdr 的 Agent 狀態，喚醒本來就用它判斷。清單讀不到時沿用上次讀到的清單；看板啟動後還沒讀到過時，所有綁定照舊顯示為啟用中。
   - 2026-10-19 補記（ouob-tw/LoopAgentTeams-work#162）：本決定只管主控名冊。看板新增的「所有 Agent」分頁以 Herdr 的 Agent 清單（`herdr agent list`）為名單來源；有接 HCOM 的 Agent 仍顯示 HCOM 的狀態，沒接 HCOM 的才顯示 Herdr 回報的狀態，因為它們沒有別的狀態來源，而 Herdr 狀態不準的問題只出現在被 HCOM 包住的 client。代價是同一分頁混用兩種狀態來源；HCOM 清單讀不到時，無法確認是否接 HCOM 的 Agent 不提供需要 HCOM 的控制。
   - 2026-10-20 補記（ouob-tw/LoopAgentTeams-work#184）：不在工作的主控只看對話在不在 hcom 清單上分兩種：已停用 LAT、對話還在的是「閒置」；對話不在的是「已關閉」，不論 LAT 有沒有停用。「已結束」不再當狀態名稱。兩者的處理方式與先前相同；看板啟動後還沒讀到過清單時，沒有綁定的主控顯示為閒置。

3. **從看板傳話，是把文字輸入到主控 client 的輸入框並送出，不用 HCOM 訊息。**
   - 為什麼：LAT 的授權規則只認使用者在對話裡說的話，HCOM 訊息不算真人核准。走輸入框，主控把它當成使用者的聊天訊息，現有規則不必修改。
   - 代價：使用者同時在該分頁打字時，兩邊的文字可能混在一起；窗格關閉或輸入失敗時只能回報失敗，沒有佇列。
   - 2026-10-14 補記（ouob-tw/LoopAgentTeams-work#126）：喚醒已結束的主控時，若它的 client 已不存在（依 hcom 的 Agent 清單、以 session ID 判斷），改用 hcom 接回同一段對話，並把文字當作接回的第一則訊息；client 還在時，傳話本身仍走輸入框。

4. **主控回報紀錄放在使用者層級的 LAT 狀態目錄，不放在各專案的 `.lat/`。**
   由既有的回合結束 hook 寫入，一個主控對話一份檔案，每筆自帶工作區路徑與主控名稱。
   - 為什麼：主控交付前就會停用，停用後面板綁定登記不再有它。回報若散在各專案，看板沒開的期間啟用又結束的主控就找不回來。放在同一個目錄，看板隨時能從回報本身找到已結束的主控。
   - 代價：回報全文可能含內網位址與本機路徑，集中存放在專案之外；看板因此要求裝置登入，且文件寫明只在內網使用。（2026-10-14 補記：原本以主機產生的配對碼綁定裝置，ouob-tw/LoopAgentTeams-work#118 改為密碼登入，此決定不變。）
   - 2026-10-16 補記（ouob-tw/LoopAgentTeams-work#130）：回報紀錄不再永久保留。一個回報檔最新一筆有效紀錄發出滿 30 天時，看板刪除這個檔案，封存也只列出 30 天內的回報。刪除透過面板輔助工具的 `board prune-reports` 執行，因為 hook 追加時用 Python 的 `fcntl.flock` 鎖檔，看板本身拿不到同一把鎖；輔助工具在鎖內再確認一次才刪，鎖檔保留，讓已在等鎖的 hook 與之後的 hook 仍共用同一把鎖。代價是刪掉的回報救不回來，已結束或已關閉的主控回報刪除後就無法從看板找回或喚醒。
   - 2026-10-21 補記（ouob-tw/LoopAgentTeams-work#212）：看板的操作紀錄（狀態目錄的 `sent-log.jsonl`）同樣保留 30 天。同一筆操作與補充它的後續行，加上模型切換與接回它的喚醒，視為一組；一組最新一行滿 30 天才整組刪除，在看板讀取時檢查（啟動後第一次，之後每滿一天一次），以暫存檔改名整份替換，權限維持 0600。看板把解析後的紀錄留在記憶體，檔案大小與修改時間沒變就不重讀；這假設看板是唯一的寫入者，所以不加跨程序鎖。開發伺服器共用同一個狀態目錄時，只保證讀到的內容正確：大小對不上就整份重讀，但兩邊同時寫或清理時仍可能互相蓋掉。代價是超過 30 天的操作不再出現在送出紀錄。
