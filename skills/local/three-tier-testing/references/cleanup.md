# 定期整理測試

整套測試閘門在距上次整理超過 30 天、或整套耗時比基準多 30% 以上時開整理票（觸發規則見 [suite-gate.md](suite-gate.md#定期整理觸發)）。接到整理票的 Agent 依本文件整理，目標是讓整套時間回到合理範圍、測試只留有用的。

## 四項工作

| 工作 | 找候選 | 怎麼處理 |
| ---- | ------ | -------- |
| 慢測試：加快或改放合適層級 | 測試工具的逐檔／逐案耗時（例如 `pytest --durations=20`、`go test -v`、jest／vitest 的 verbose 輸出）；閘門紀錄的整套耗時（`suite-gate.py status --json` 的 `duration_s`）看是哪一套變慢 | 去掉不必要的固定等待（`sleep`、逾時重試），共用昂貴的建置或資料準備；不需要真實服務的整合測試改寫成單元測試；E2E 只留關鍵使用者流程，其餘分支改由較低層涵蓋 |
| 重複測試：合併或刪除 | 名稱或斷言相近的測試；同一行為在多層重複驗證（例如單元與整合都驗同一條驗證規則）；只差輸入值、複製貼上的測試 | 只差輸入值的合併成參數化測試；多層重複時留最低能測到該行為的那一層，其餘刪除 |
| 已移除功能與長期跳過的測試：刪除 | 測試引用的模組、路徑或端點已不存在；跳過標記（`pytest.mark.skip`、`unittest.skip`、`it.skip`、`test.skip`、`xit`、`t.Skip`、`#[ignore]` 等），用 `git log -S` 或 `git blame` 查跳過多久 | 對應功能已移除的直接刪；跳過超過 30 天且沒有追蹤中的票就刪除，還要保留的改成正常執行或開票追蹤 |
| 時好時壞的測試：修好 | 閘門紀錄中同一份內容有通過也有失敗（`status --fingerprint <開頭>`）；`--rerun` 原因提到偶發失敗；CI 重跑紀錄 | 先查出原因（時間或時區、執行順序、共用狀態、port、網路、未等待的非同步），修好後對該測試檔做一次重複跑；不以連跑多次整套作為證明 |

不在整理範圍：檢查放錯層的測試、日常更新對照表（新增檔案時由實作者順手補，見 [suite-gate.md](suite-gate.md#受影響測試與對照表)）。

## 處理原則

- 刪除與合併直接做，不必逐項等使用者核准；由獨立審查把關。
- 整理內容（PR 或整理票留言）逐項列出刪除、合併、改層與修正的測試及理由，讓審查者核對：
  - 被刪或被合併的測試所驗證的行為，是否仍有其他測試涵蓋（已移除的功能除外）。
  - 改層或改寫後是否仍測到同一件事，沒有只是把斷言拿掉。
  - 修好的偶發失敗是否說明了原因並附重複跑的結果。

## 沒有對照表的專案

專案登記檔還沒有受影響測試對照表時，第一次整理一併建立（欄位與範例見 [suite-gate.md](suite-gate.md#對照表欄位)），之後每張票改跑受影響測試。

## 收尾

整理合併、準備關閉整理票時：

1. 在專案內執行 `suite-gate.py cleanup-done`：上次整理日改為當天並開始新視窗，舊的耗時樣本不再計入。基準預設取新視窗的第一筆可沿用通過；已量到整理後的耗時，也可以用 `--command '<整套指令>' --baseline <秒數>` 直接指定。
2. 經閘門跑一次整套（有對照表的專案要標用途，例如 `run --reason "test cleanup"`），這次通過就是新基準。
3. 在整理票回報整理前後的耗時與處理清單，再關票。
