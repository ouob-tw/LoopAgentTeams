# 視覺驗收

## 任務卡欄位

`視覺驗收` 欄必填，一行，由主控派工時填好，並寫進第一則任務訊息；`lat-dispatch.py` 的 `card --visual-acceptance` 與 `brief` 都會檢查，`brief` 原樣帶入。任務會改變使用者看得到的東西（畫面、動畫、網頁、圖表）時寫三件事，否則填「無」：

- 看什麼：要看的畫面或動作，含動作過程與轉場。
- 對照什麼：參考圖路徑或使用者選定的樣子；都沒有就寫使用者描述的原話。
- 怎樣算錯：一眼看得出來的錯誤樣子。

範例：

```markdown
- 視覺驗收：看日出動畫的水面（靜止、起浪中、切換場景）；對照使用者選定的 sea-b.png；水面出現尖峰、黑塊或像固體算錯
```

缺少或留空時，[停住監控](stall-watch.md#任務卡必填欄位檢查) 會通知主控補上。

## 交付與判讀

這欄不是「無」時，依序做完下列四項才算通過驗收：

1. **逐格圖**：實作者把每個改到的樣子各截一格，有動作的畫面另含動作中段與轉場的格，放進該票 `runs` 資料夾並回報路徑。格數與改動相稱，靜態小改一張就夠。網頁先在真實瀏覽器打開、操作每個切換、確認主控台沒有錯誤再截圖。
2. **判讀**：實作者以外的人（主控或獨立判讀者）直接看圖，對照使用者想要的樣子，逐項寫下看起來對或不對及理由，記在 `runs` 與測試清單。獨立判讀者只拿使用者的要求、參考圖與逐格圖，判斷才不會跟著實作者的說法走。判讀不對記 `FAIL`，交回實作者；還沒有人看過記 `UNPROVEN`。測試全過、審查通過、符合原型都不算看起來對。
3. **原型與參考圖**：原型或參考圖本身看起來就不對時，依 SKILL.md「使用者待決事項」提出來，不照抄。
4. **缺陷轉門檻**：看出來的缺陷能量化就轉成可測門檻（例：水面高度上限 5%，有問題的版本 86.9%），測試須在有問題的版本上失敗，版本、指令與結果記在 `runs`。無法量化時寫明，改以逐格圖複驗。修好後仍要重新判讀，門檻只防同一缺陷再犯。

要給使用者看的成果（含原型），主控送出前自己看過圖，不只轉述 Agent 的報告。
