# Spec 文件審查

Spec 寫好之後、請使用者確認之前，由獨立審查者拿使用者的原始答覆對照 Spec，找出必須修的問題。它審的是 Spec 本身；/code-review 的 Spec 面向是實作後檢查程式有沒有照 Spec 做。兩者各自要做，互不取代。

## 何時審查

- 預設每份 Spec 都審。
- 下列三項都成立時「可以」跳過，不是必須跳過：預計一張票做完；不動到資料或存檔格式；不跨模組。跳過時在 Spec 寫明理由，逐項說明三項如何成立。
- 使用者明確指定這份 Spec 要審或不審時，從其指定，並在 Spec 註明是使用者指定。
- 由主控判斷是否審查；Designer 認為「應該沒問題」不是跳過理由。
- 使用者確認後 Spec 又有實質改版時，見下方「確認後改版」。

## 職責

- **主控**：判斷是否審查、派審查者、核對證據、發確認題與收尾。
- **Designer**：修正 Spec 並寫修正說明。
- **審查者**：只提出問題，不改 Spec。審查者不兼任 QA；QA 仍依 SKILL.md「測試清單」從需求獨立列情境。

## 派審查者

審查者是全新 context 的 Agent，不是寫 Spec 的 Designer，並且與 Designer 用不同家模型。模型選擇與模型不可用時的處理見 [Agent 設定](agents.md#派工)。審查者照常建立任務卡。

任務訊息交給審查者：

- Spec 位置（tracker issue）。
- 相關 `.lat/decisions/` 紀錄的絕對路徑，內含使用者答覆原文。
- 專案詞彙表與 ADR 的位置（依專案設定）。
- 專案的唯讀存取：可讀程式碼與設定，不改任何檔案。
- 下方四個檢查面向與問題格式。

只交上述原始資料。Designer 對討論過程的摘要或轉述不放進任務訊息，避免審查者被同一套說法帶著走。

## 檢查面向

1. **忠實**：Spec 是否反映使用者講過的話與已做的決定，包括漏掉的與多加的。
2. **清楚**：有沒有含糊不清或前後矛盾的地方。
3. **可行**：對照專案實際的程式、設定與既有規則，做不做得到。
4. **可驗證**：每個驗收條件能不能實際看到結果，包括失敗與恢復的情況。

## 問題分級與格式

只有以下四種算「必須修」，會擋住流程：

- 與使用者的決定衝突，或漏掉／多加需求。
- 含糊或矛盾到會被做成不同結果。
- 在專案裡做不到。
- 驗收條件無法驗證。

其餘（措辭、排版等）是「建議」：不擋流程，也不進入重審；Designer 自行決定是否採納。

審查者用以下表格回報，編號用 `R<輪>-<序>`，最後一行寫判定：

```markdown
| 編號 | 等級（必須修／建議） | Spec 位置 | 依據（決策紀錄或程式位置） | 問題 | 建議修法 |
|---|---|---|---|---|---|

判定：通過｜N 項必須修
```

沒有必須修的項目就是通過。

## 修正與重審

- Designer 逐項處理必須修項目，寫修正說明：`編號 | 處理 | 改動位置`。
- 修法等於改變或新增需求時，Designer 不自行決定，交主控依 SKILL.md「使用者待決事項」記錄並提問。真人答覆前，Spec 該處不做相依修改；其他項目照常修正與重審。答覆後修正，下一輪只重審受影響部分。
- Designer 不同意某項必須修時，在修正說明寫明理由交回審查者；審查者仍維持時，列為意見不合，不再來回，連同雙方說法列入確認題。
- 修完交回**同一位**審查者（同一個對話），只重看上一輪的必須修項目與這次改動的地方，不從頭審。
- 審查者中途失聯：先依 /hcom-spawn 的恢復程序接回同一位，保留它的對話。接回不了時，改開同款模型的全新審查者，除上方原始資料外，再交給它前幾輪的審查留言與修正說明；輪數接續計算、不歸零，新留言標示接續的輪數並引用前幾輪留言。模型仍可用時這一步不需問使用者。

## 輪數上限

一輪就是一次審查，第一次審查算第 1 輪。最多 3 輪（試行值）。第 3 輪後仍有必須修的項目，不再修，原樣連同審查者與 Designer 雙方說法列入確認題，由使用者裁定。

## 記錄與確認題

- 每輪的審查結果與修正說明，由主控（或 Designer）貼在 Spec 的 tracker issue 留言，標題寫 `Spec 審查 第 N 輪`、`第 N 輪修正說明`。完整清單只放在留言。
- 確認題內文只附一行審查結論，加上未解決項目（含雙方說法），不附審查過程：
  - `Spec 審查：通過（共 N 輪）`
  - `Spec 審查：還有 N 項沒解決`，接著列出這些項目
  - `Spec 審查：跳過，理由：…`
- 發確認題前，主控核對可查證據：每輪留言都在 issue 上，輪數與結論相符；跳過時 Spec 寫有理由。只憑 Designer 說「審過了」不算。
- 審查還在進行、等待模型恢復或等待相關待決答覆時，不發 Spec 確認題。

## 確認後改版

已確認的 Spec 實質改版（需求、範圍或驗收條件有變）時，依本文件派審查者，交給它原始資料、前次審查留言與這次改動的差異，只審改動部分。結果同樣貼在 issue 留言，再發新版確認題並保存真人答覆。

## 收尾

文件審查沒有 commit，不適用 [任務收尾](task-cards.md#任務收尾) 的合併門檻。使用者確認 Spec，或決定放棄這份 Spec 後，主控依 [Agent 設定](agents.md#收尾) 關閉審查者，任務卡 status 改為 `completed`、deliverable commit 填「無（證據為 issue 留言）」並移到 `.lat/tasks/done/`。
