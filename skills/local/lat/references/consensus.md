# Spec 共識

Designer 用 /to-spec 整理正文後、發布或更新 tracker 前，在 issue 內文最上面寫共識。使用者確認的是 issue 上的共識；執行 Agent 仍按正文實作。任何角色發現兩份不一致，都當作 Spec 有錯，停止受影響工作並回報主控，修正後依待決程序重新確認。

## 寫法與更新

```markdown
**共識 v1**
- **目標**：一句白話結論。
  - 一句講不完才加補充。
- **不做**：這次不包含的事。
- **你要留意**：代價、極限或使用者口頭同意過的事。

# Spec 正文
```

- 第一個非空行固定為 `**共識 v<N>**`，N 從 1 開始；共識到第一個 `#` 開頭的標題行之前結束。至少一條第一層 `- **主題**：結論`（全形冒號，兩者不可空白），補充用兩個空格加 `- `，最多兩層；區塊內只有條目與空行。
- 一個主題一條、結論盡量一句話，用繁體中文與白話，不寫檔案路徑或程式細節。保留主題出現時排在其他主題後，順序固定為「已拿掉 → 不做 → 你要留意」；沒有內容就整條省略。
- 每次修改 Spec 都檢查共識是否仍正確。共識文字有變就升版（+1），正文變但共識不變則不升版；共識版本與題目 r 版本獨立。需求、範圍或驗收有變才重審改動部分、重新確認。
- 以上次真人確認版本為準：之後改動或新增的條目，行尾加 `（v<M> 改）`，M 是最後變動版本。連續改版未確認時保留各版記號；確認後，下一次改版才移除已確認版本以前的記號。尚未確認過時不需要記號。
- 整條主題或補充被拿掉時，在「已拿掉」下逐項簡述並帶記號；確認後下一次改版移除。v1 不得有記號或「已拿掉」。記號版本須滿足 2 ≤ M ≤ 目前版本，且大於上次確認版本（如有）。

## 發確認題前

1. Designer 可先只檢查。主控依專案 tracker 設定取得 Spec 內文，保存為檔案或交給標準輸入；工具不連網、不比對前後版本的實際差異，也不判斷內容是否正確、完整或白話，這些由 [Spec 文件審查](spec-review.md) 核對。跳過審查仍須通過工具。
2. 建好 Spec 確認題的待決紀錄後，執行下列命令。`lat_dir` 是目前載入的技能目錄；其他參數使用本專案的真實位置與 ID。

```bash
uv run --no-project python "$lat_dir/scripts/lat-consensus.py" \
  --spec "$spec_body" --decisions "$decisions" --decision-id "$question_id"
```

省略 `--decision-id` 時只檢查，不寫任何檔案；`--spec -` 讀標準輸入。已有真人確認版本時另加 `--last-confirmed-version <版本數字>`。

不合格會列出原因與行號、非零結束，待決紀錄不變。通過印出並寫入唯一一行 `- consensus: v<N> <sha256>`；同內容可重跑，內容變更會更新。雜湊去除每行行尾空白與區塊前後空行；紀錄不存在時報錯，不建立檔案。Spec 每次修改都重跑。

3. 聊天與面板的題目內文相同，寫 issue 連結與固定格式 `共識 v<N>`，接既有的一行審查結論與未解決項目；聊天不重貼共識全文。重新確認時，在同一則訊息、題目前用條列說明這次改了哪幾條及拿掉什麼，對應帶記號的條目；這段由主控撰寫，不交 Spec 審查者審，也不由 hook 核對。
4. 收到真人答覆時，待決紀錄保存所確認的共識版本與答覆來源。回合結束檢查的補做方式及限制見 [主控恢復](recovery.md#回合結束檢查)。

## 既有 Spec

已確認且未實質改版的舊 Spec 不補共識。上線時尚未答覆的舊確認題，原訊息不受影響，之後重問才須先補共識、跑工具。舊 Spec 實質改版而需重新確認時，從共識 v1 開始，不需要記號。Ticket 不加共識；面板不顯示共識全文。
