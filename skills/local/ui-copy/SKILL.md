# 介面呈現

畫面要讓人一眼看懂內容，不必先讀說明。

## 呈現順序

每項資訊依序選呈現方式，前一層做得到就不往下：

1. **圖形**：圖示、顏色、狀態標記、排版（分組、位置、大小、對齊）。例如狀態用色點加圖示，不寫「目前狀態：執行中」；相關的項目排在一起，不用文字說明它們相關。
2. **收合**：tooltip、展開區、二級選單。放只有部分人、偶爾才需要的細節，例如完整路徑、時間戳、錯誤細節。
3. **畫面上的文字**：前兩層表達不了，而且符合下面「加不加」的才寫。

- 顏色搭配圖示或形狀一起用，不靠顏色單獨區分。
- 圖示意思不明顯時，用 tooltip 補上名稱。

## 加不加

畫面上的文字預設不加。多一句就多一份要讀、要維護、要在各處保持一致的東西。只在兩種情況加：

- 使用者明確要求這段文字。
- 沒有這句，多數使用者會卡住或做錯，例如不可逆動作的後果、失敗後下一步該做什麼。

兩者都不是就不加。先試著改圖形、標籤名稱或預設值，改得掉就不用補說明。

## 怎麼寫

- 一句話。第二句通常是在解釋第一句，刪掉。
- 副標、提示不重複標題已經說過的內容。
- 不解釋畫面上已經看得出來的行為，例如按鈕按下去會做什麼，名稱已經說了。
- 同一個訊息沿用專案裡已有的措辭。先搜尋既有字串，找到就重用或抽成共用常數，不在不同模組各寫一版。

失敗與不可逆動作的提示：一句話講結果，再講下一步。

```text
壞：操作未能成功完成，可能是網路不穩或伺服器忙碌，請稍後再試或聯絡管理員。
好：沒有送出，請檢查網路後再按一次。
```

## 寫需求或票

寫使用者要看出什麼、達成什麼，不寫整句措辭，也不指定用文字呈現，例如「關閉前要讓使用者知道能不能接回」。使用者指定了措辭才照抄。呈現方式與措辭交給實作者依上面的規則決定，避免需求裡的預寫句子被當成必加文字。

## 實作

- 先照「呈現順序」選圖形或收合，畫面上的文字只加需求或驗收條件列出的。
- 需求只給目的、又非用文字不可時，用一句話寫出來，並套用「怎麼寫」。
- 測試或審查要求補文字時，先確認圖形或收合做不到、且符合「加不加」，再加。

## 審查

說「介面沒解釋 X」的意見，要附上使用者實際會卡住的情境：誰在哪一步會做錯什麼。附不出來就不算缺陷。

可以建議的修法優先序：改圖形、排版、標籤或預設值，其次收進 tooltip 或展開區，再其次一句話，最後才是更長的說明。同時檢查這次變更是否加了不必要的文字，或把能用圖形表達的資訊寫成字，有就提出刪除或改成圖形。
