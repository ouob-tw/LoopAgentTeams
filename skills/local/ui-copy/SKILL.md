# 介面文字

介面文字預設不加。多一句就多一份要讀、要維護、要在各處保持一致的東西。

## 加不加

只在兩種情況加：

- 使用者明確要求這段文字。
- 沒有這句，多數使用者會卡住或做錯，例如不可逆動作的後果、失敗後下一步該做什麼。

兩者都不是就不加。先試著改標籤名稱或預設值，改得掉就不用補說明。

## 怎麼寫

- 一句話。第二句通常是在解釋第一句，刪掉。
- 副標、提示不重複標題已經說過的內容。
- 不解釋畫面上已經看得出來的行為，例如按鈕按下去會做什麼，名稱已經說了。
- 同一個訊息沿用專案裡已有的措辭。先搜尋既有字串，找到就重用或抽成共用常數，不在不同模組各寫一版。

失敗與不可逆動作的提示：一句話講結果，再講下一步。

```text
壞：操作未能成功完成，可能是網路不穩或伺服器忙碌，請稍後再試或聯絡管理員。
好：沒有送出。請檢查網路後再按一次。
```

## 寫需求或票

寫要達成的目的，不寫整句措辭，例如「關閉前要讓使用者知道能不能接回」。使用者指定了措辭才照抄。措辭交給實作者在上面的規則內決定，避免需求裡的預寫句子被當成必加文字。

## 實作

- 只加需求或驗收條件列出的文字。沒列的說明句不加。
- 需求只給目的時，用一句話寫出來，並套用「怎麼寫」。
- 測試或審查要求補文字時，先確認它符合「加不加」，再加。

## 審查

說「介面沒解釋 X」的意見，要附上使用者實際會卡住的情境：誰在哪一步會做錯什麼。附不出來就不算缺陷。

可以建議的修法優先序：改標籤或預設值，其次一句話，最後才是更長的說明。同時檢查這次變更是否加了不必要的文字，有就提出刪除。
