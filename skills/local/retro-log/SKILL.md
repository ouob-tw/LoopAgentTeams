# 記錄 retro 反饋

反饋庫是所有專案共用的本機 git repo，由小程式管理。計數、狀態、復發、排序、去重與 git commit 都由小程式負責，你負責判斷「是不是同一個問題」「是否嚴重」，並撰寫條目內容。條目檔只透過小程式改動。

小程式：`uv run --no-project python <本次實際載入的本技能目錄絕對路徑>/scripts/retro-log.py <指令>`，下文簡寫為 `retro-log <指令>`。條目編號一律寫成「retro #N」，避免被當成 issue 編號；其他 session 只要查條目，執行 `retro-log show <N>`（主機的 `~/.local/bin/retro-log` 捷徑會執行已安裝的小程式），不必找技能路徑。各指令參數見 `retro-log <指令> --help`。指令被拒時照訊息修正後重跑，下方 Gotchas 另有規定的除外。

## 模式

參數含 `流程` 就是**流程模式**：只處理當前對話，全程不問使用者。其餘一律是**人類模式**：寫入前由使用者勾選。

## 記錄一次 retro

1. **找反饋來源**：本對話已有 /retro 結果就用它。使用者指定其他 session（補匯入）時，讀那個 session 的紀錄（Claude：`~/.claude/projects/*/<session>.jsonl`；Codex：`~/.codex/sessions/**/rollout-*-<session>.jsonl`）中的 /retro 結果。還是沒有結果，就讀本技能目錄旁的 `../retro/SKILL.md`，照它分析指定的 session（沒指定就是本對話），列出建議後接著做第 2 步。讀不到這份檔案就停下告訴使用者，分析只照它做。
2. **逐條分類**：依下方「記錄範圍」與「去向」，定出每條建議的類型與去向。一次性的建議到此結束，列入摘要的略過。
3. **選出要處理的**：
   - 流程模式：範圍內的建議全部處理。
   - 人類模式：用 AskUserQuestion 複選題讓使用者勾選，選項寫標題與一句說明。每題放一類，依序是開 issue、緊急、會再遇到、小問題與不順手；跳過空的類，只有一條的類和下一類合成一題（最後一類和上一類合），選項標出類型。全部只有一條時改用單選題問要不要處理。一次最多 4 題、每題 2–4 個選項，放不下時排除最不重要的，列入摘要的未列入選單。沒有這個工具的 client 改列編號，由使用者回編號。沒勾的建議不寫入，列入摘要的沒勾。
4. **定出共用欄位**：
   - `--client`：`claude` 或 `codex`，看反饋來源的 session 是哪個 client。
   - `--session`：本對話用 `$CLAUDE_CODE_SESSION_ID`（Claude）或 `$CODEX_THREAD_ID`（Codex）；其他 session 用它的 session ID。
   - `--project`：該 session 工作的 git repo 名稱（主 worktree 的資料夾名，不是 `.worktrees/` 下的分支資料夾）。
   - `--time`：有 /retro 結果時，用該 session 中觸發 /retro 那則使用者訊息的時間戳記；由本技能分析時，用觸發本技能那則使用者訊息的時間戳記；查不到時用該 session 最後一則紀錄的時間。流程模式用 `date --iso-8601=seconds` 取一次當下時間。
5. **開 issue**（去向是 issue 的建議）：讀該專案的設定，依它寫的位置與慣例操作。
   - 先搜尋相同問題。已有就不開新的：這次有 issue 和留言裡還沒寫到的新證據時，留一則一句話的留言；沒有就不留。
   - 新開時標 `needs-triage` 與 `bug` 或 `enhancement`；該 repo 沒有這些標籤就不標。
   - 內文用繁體中文寫問題、影響、建議做法與證據，去除內部主機、本機路徑、帳號與 session 細節。
   - 開 issue 失敗時改記進反饋庫，摘要註明原因。
6. **逐條搜尋**（去向是反饋庫的建議，第 6–8 步同）：每條反饋用兩三組關鍵字（含同義詞、中英文說法）跑 `retro-log search <關鍵字…>`，再對看起來相關的候選跑 `retro-log show <編號>` 讀全文。搜尋只比對字面，措辭不同的同一問題要靠換關鍵字找。結果顯示「已併入 retro #N」時改看 retro #N。
7. **判斷相同、新開或拿不準**：
   - **相同**：根本原因相同，同一個修法能同時解決。用 `retro-log occur <編號> …`。
   - **新開**：沒有候選，或候選明顯是別的問題。用 `retro-log add …`。
   - **拿不準**：有候選但無法確定是同一問題。用 `retro-log add … --suspected <候選編號…>`。
   - 新開時用繁體中文寫：`--title` 一句話說問題；`--description` 發生了什麼、在哪裡；`--suggestion` retro 建議的做法。`--evidence` 一律寫一句這次 session 的具體證據。
8. **標嚴重**：類型是緊急時寫一句理由，說明符合哪一項、依據這次的什麼事實。新開用 `add --severe <理由>`；記到既有條目且該條目目前不嚴重時，再跑 `retro-log severe <編號> --reason <理由> --time <同一個時間>`。
9. **印出摘要**：全部寫完後跑 `retro-log list --status ready --limit 3`，依下方格式回覆。新開、併入、拿不準三份清單依第 7–8 步各指令的輸出整理；小程式回「已存在」的條目列在併入，註明未加次數。

```markdown
**本次寫入**
- 開 issue：owner/repo#7 標題；owner/repo#3 標題（已有相同 issue，補留言）
- 新開：retro #12 標題；retro #13 標題
- 併入舊條目：retro #4 標題（現 2 個 session，轉可處理）
- 拿不準：retro #13 疑似 retro #7；確認相同可說「把 retro #13 併入 retro #7」
- 略過：一句話說明（一次性）
- 未列入選單：一句話說明；要記可直接說
- 沒勾：一句話說明；要記可直接說

**可處理前三名**
1. retro #4 標題［嚴重］：一句話說明問題與影響
2. …
3. …

**推薦先做**：retro #4，一句理由。
```

某一類清單是空的就寫「無」，可處理前三名與推薦先做也一樣。可處理不到三筆就列現有的。修問題不是本技能的工作；使用者挑中後照平常方式處理。

## 記錄範圍

| 類型 | 判斷方式 | 處理 |
| --- | --- | --- |
| 緊急 | 符合任一項：錯誤成品被交付、資料或檔案損毀、耗費大量時間或額度 | 處理，進反饋庫時標嚴重 |
| 會再遇到 | 造成問題的原因還在，下次走到同一步還會發生 | 處理 |
| 小問題與不順手 | 影響小，但原因還在 | 處理 |
| 一次性 | 只發生一次，原因已消失 | 略過 |

## 去向

看修的時候要改哪裡，不看問題發生在哪。依序比對，第一條符合的就是去向：

1. 來源專案沒寫明 issue 位置（`docs/agents/issue-tracker.md` 或它的 `CLAUDE.md`、`AGENTS.md`）→ 反饋庫。
2. 只改來源專案的檔案就能修好（bug 與非 bug 都算）→ 該專案的 issue。來源專案是 LoopAgentTeams 時，只有確定壞掉的才算。
3. 其餘 → 反饋庫，包括要改技能、全域設定、hook 或主機工具的問題，以及對 LAT 流程的意見。

## 其他用法

使用者要求時才做，做完印出小程式的結果那一行。

| 使用者要的 | 指令 |
| --- | --- |
| 關鍵字查詢 | `search <關鍵字…>` |
| 依狀態列清單 | `list --status <狀態>`；有疑似標記的 `list --suspected`；已併入的 `list --merged` |
| 看單一條目 | `show <編號>` |
| 手動合併（確認拿不準的是同一問題） | `merge <被併的> <保留的>` |
| 確認拿不準的是不同問題 | `unsuspect <編號>` |
| 標已完成 | `done <編號> --commit <sha>` 或 `--file <路徑>`；補記過去的修好用 `--time <commit 提交時間>` |
| 標不做 | `wontfix <編號> --reason <理由>` |
| 手動設可處理 | `ready <編號>` |
| 改嚴重或取消嚴重 | `severe <編號> --reason <理由>`；取消用 `severe <編號> --unset` |
| 改既有處理紀錄的時間 | `retime <編號> --from <原時間> --to <新時間>` |

## Gotchas

- 照訊息跑 `retro-log restore` 時，把它列出的捨棄檔案告訴使用者。
- 合併因兩筆處理紀錄時間相同而被拒時，先後由使用者決定：把列出的衝突原樣交給使用者，問哪一筆在前、要改成什麼時間，照回答用 `retime` 改那一筆，再重跑同一個 `merge`；衝突的是「合併新增」那筆時，改成在 `merge` 加 `--time <新時間>` 重跑。不自行決定先後，也不另記一筆新紀錄代替改時間。
- 測試或試跑時設 `RETRO_BACKLOG_DIR` 指向暫存資料夾，避免寫進真正的反饋庫。
